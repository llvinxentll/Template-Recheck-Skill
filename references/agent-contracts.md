## หลักการออกแบบ — ทำไมต้องแบ่งแบบนี้

แบ่งตาม **ส่วนของเอกสารที่ต้องอ่าน** ไม่ใช่ตามหัวข้อที่ต้องตรวจ เพราะถ้าแบ่งตามหัวข้อ
(ตัวหนึ่งตรวจ format ตัวหนึ่งตรวจ APA) ทั้งสองตัวยังต้องอ่านเล่มเดียวกันทั้งเล่มอยู่ดี —
context บวมเท่าเดิม แค่ทำงานพร้อมกัน. พอแบ่งตามส่วนของเอกสาร แต่ละ agent เห็นข้อความ
คนละก้อนที่ไม่ทับกัน context จึงเล็กลงจริงตามจำนวน agent

เส้นแบ่งสามเส้นนี้ยังตรงกับ "ชุดกฎที่ต้องจำ" พอดี ซึ่งสำคัญไม่แพ้กัน:

| Agent | อ่านไฟล์ | ชุดกฎที่ต้องโหลด | ทำไมแยก |
|---|---|---|---|
| 1 | `frontmatter.txt` | inspection-checklist หมวด B1–B4 | ส่วนนำมีกฎเฉพาะตัวเยอะมาก (ลำดับบรรทัดบนปก, แบบหน้าอนุมัติ, 6 รายการในบทคัดย่อ) แต่ใช้กับ ~10 หน้าแรกเท่านั้น |
| 2 | `body*.txt` + `backmatter.txt` | inspection-checklist หมวด B5–B7 | เนื้อหา/ภาคผนวกเป็นก้อนใหญ่สุดแต่กฎน้อย เหมาะจะซอยเพิ่มถ้าเล่มหนา |
| 3 | `references.txt` + `intext.txt` | คู่มือ APA7 ไทย/อังกฤษ | เป็นคนละมาตรฐานกันคนละเล่ม ถ้าให้ตัวเดียวกับ format จะสลับกฎมั่ว |

**ตัวตรวจอัตโนมัติไม่ต้องใช้ agent** — รัน `check_all.py` เพื่อโหลด DOCX ครั้งเดียวและสร้างผลของ
`check_docx.py` + `check_deep.py`. สำคัญ: สองชุดนี้ทำงานให้เยอะกว่าที่คิด (สารบัญ, caption,
เลขบท, APA7 เชิงกลไก) — prompt ของแต่ละ agent จึงระบุไว้ชัดว่าอะไร "ไม่ใช่" งานตัวเอง
ถ้า agent ไปไล่ซ้ำจะช้าขึ้นเปล่า ๆ แถวในรายงานก็ซ้ำ

## รูปแบบผลลัพธ์ที่ทุก agent ต้องส่งกลับ

agent **เขียนไฟล์ JSON หนึ่งไฟล์** แล้วตอบกลับแค่ path + สรุปสั้น ๆ
(ห้ามตอบ finding ทั้งก้อนกลับมาเป็นข้อความ — จะไปบวม context ของ orchestrator แทน
ซึ่งทำให้ที่อุตส่าห์แบ่งมาเสียเปล่า)

```json
{
  "agent": "frontmatter",
  "findings": [
    {
      "domain": "template",
      "severity": "critical",
      "location": "แผ่นที่ 1 · หน้าปกใน",
      "category": "หน้าปก",
      "issue": "ปีการศึกษาเขียน '2024' (ค.ศ.) บนปกภาษาไทย",
      "criterion": "เทมเพลตไทย rev.2024 กำหนดให้ปกไทยใช้ พ.ศ.",
      "fix": "แปลงปี ค.ศ. เป็น พ.ศ. โดยบวก 543 แล้วแก้บรรทัดปีการศึกษา",
      "correct": "ปีการศึกษา 2567"
    }
  ]
}
```

**ฟิลด์** (ทุกฟิลด์เป็น string ยกเว้น `findings` ที่เป็น array)

| ฟิลด์ | ค่าที่ใช้ได้ | หมายเหตุ |
|---|---|---|
| `domain` | `template` \| `spelling` \| `apa7` | ตาราง 1/2/3 ตามลำดับ; ปัญหาระดับคำ/อักขระใช้ `spelling` |
| `severity` | `critical` \| `major` \| `minor` | critical = ส่งไม่ผ่านแน่ ๆ (ระยะขอบ/ฟอนต์ทั้งเล่ม/โครงสร้างขาด), major = ต้องแก้แต่ไม่ตีกลับทั้งเล่ม, minor = จุกจิก |
| `location` | ข้อความอิสระ | **เลขแผ่น + คำบอกส่วน** เช่น "แผ่นที่ 12 · หน้าปกใน" — ลอกเฉพาะเลขแผ่นจากป้าย `[sheet12\|…]` **ไม่ต้องใส่ ¶** (รายงานตัดทิ้งเสมอ). ⚠️ เลขแผ่นนี้เป็น**ค่าประมาณ** ใช้เรียงลำดับแถวเท่านั้น — **ห้ามเอาไปเขียนใน `issue`** และห้ามใช้สรุปว่าอะไรข้ามหน้า/เกินหน้า (กฎความแม่นยำข้อ 3) |
| `snippet` | ข้อความ (**ควรใส่**) | ข้อความต้นฉบับตรงจุดที่ผิด ก๊อปมาเป๊ะ ๆ จาก slice — รายงานเอาไปแสดงเป็น "คำค้น" ให้ผู้อ่านวางใน Ctrl+F. **ต้องเป็นข้อความที่มีอยู่จริงในเล่ม ไม่ใช่ข้อความที่แก้แล้ว** ไม่งั้นรายงานจะติดธง ⚠ ว่าค้นไม่พบ |
| `category` | ข้อความสั้น | ใช้จัดกลุ่มในตาราง เช่น "หน้าปก", "สารบัญ", "caption ภาพ", "APA7 ไทย" |
| `issue` | ข้อความ | สิ่งที่**พบจริง** — **ยกข้อความต้นฉบับใส่เครื่องหมายคำพูด** ไม่ใช่เขียนว่า "รูปแบบไม่ถูกต้อง" ลอย ๆ. ข้อความที่ยกมานี้คือสิ่งที่ผู้อ่านรายงานเอาไปค้นใน Word ถ้าไม่มี แถวนั้นจะบอกได้แค่ "ทั้งเอกสาร" ซึ่งช่วยอะไรไม่ได้ |
| `criterion` | ข้อความ | **เกณฑ์ที่ใช้ตัดสิน** พร้อมอ้างว่ามาจากไหน (docx-spec ข้อไหน / กฎ APA7 ข้อไหน) |
| `fix` | ข้อความ | ขั้นตอนแก้ใน Word/ข้อความที่ทำตามได้ทันที |
| `correct` | ข้อความ | ค่า/ข้อความที่ถูกต้องแบบเป๊ะ ๆ พร้อมก๊อปไปวาง — APA7 ครอบส่วนที่ต้องเอียงด้วย `*...*` |

**กฎที่ทุก agent ต้องยึด** (เหมือนกับโหมดปกติ ดู "กฎความแม่นยำ" ใน SKILL.md):
ตรวจจากข้อความใน slice เท่านั้น · ไม่มีหลักฐานอย่า flag · ไม่แต่งข้อมูล (DOI/ปี/เลขหน้าที่ไม่มีในต้นฉบับ) ·
ตรวจไม่ได้ให้เขียนใน `issue` ว่า "ตรวจไม่ได้จาก slice นี้ ต้องเปิดดูใน Word" · ถ้าส่วนนั้นไม่มีปัญหา
ส่ง `"findings": []` กลับมา **ห้ามหาเรื่องเติมให้ครบโควตา**

## Agent 1 — รูปแบบเทมเพลต (ส่วนนำ)

```
คุณคือผู้ตรวจรูปแบบส่วนนำของวิทยานิพนธ์ มหาวิทยาลัยธรรมศาสตร์

อ่านไฟล์เหล่านี้ก่อนเริ่ม:
  <SKILL>/references/inspection-checklist.md   (ตรวจเฉพาะหมวด B1–B4)
  <SKILL>/references/docx-spec.md              (เกณฑ์ตัวเลขของ profile <PROFILE>)
ชิ้นงานของคุณ: <WORK>/frontmatter.txt
  ทุกบรรทัดมีป้าย [sheet<แผ่น>|¶<ย่อหน้า>] — **ลอกไปแค่เลขแผ่น** เช่น location = "แผ่นที่ 12"
  ไม่ต้องใส่ ¶ (รายงานตัดทิ้งอยู่แล้ว) แต่ **ต้องยกข้อความจริงที่ผิดใส่เครื่องหมายคำพูดใน issue**
  ⚠️ เลขแผ่นเป็นค่าประมาณ ห้ามเขียนลงใน issue และ **ห้ามใช้สรุปว่าอะไรข้ามหน้า/เกินหน้า**
  เกณฑ์ B1 (องค์ประกอบปกอยู่หน้าเดียว) · B3 (บทคัดย่อ ≤ 1 หน้า) · B4 (กิตติกรรมประกาศ ≤ 1 หน้า)
  ออก finding ได้ต่อเมื่อ orchestrator ส่ง pagemap.json มาให้ ถ้าไม่มีให้ข้ามเกณฑ์นั้นไปเลย

ขอบเขต — ตรวจเฉพาะ 4 อย่างนี้ อย่าไปยุ่งกับส่วนอื่นของเล่ม:
  B1 ปกใน/ปกภาษาที่สอง — องค์ประกอบครบและเรียงถูก (ชื่อเรื่อง/โดย-BY/ผู้เขียน/
     หลักสูตร/ภาควิชา/คณะ/มหาวิทยาลัย/ปีการศึกษา), ปกไทยใช้ พ.ศ. ปกอังกฤษใช้ ค.ศ.,
     ชื่อผู้เขียนไม่มีคำนำหน้า (นาย/นาง/นางสาว), คำติดกันเพราะเว้นวรรคหาย
  B2 หน้าอนุมัติ — ใช้แบบเดียว (มี/ไม่มีที่ปรึกษาร่วม) ห้ามผสมสองแบบ,
     กรรมการครบตามแบบ, มีเส้นเซ็นชื่อ + วงเล็บ (ตำแหน่งวิชาการ ชื่อ สกุล), วันที่ + คณบดี
  B3 บทคัดย่อ (ทั้งสองภาษา) — ตารางข้อมูลครบ 6 รายการ, หัวข้อกึ่งกลาง,
     เนื้อหาไม่เกิน 1 หน้า, "คำสำคัญ:"/"Keywords:" ต้องเป็นตัวหนา (ไม่ใช่ "Keyword")
  B4 กิตติกรรมประกาศ + สารบัญ — กิตติกรรมประกาศไม่เกิน 1 หน้า ชื่อผู้เขียนชิดขวาท้ายหน้า,
     สารบัญมีครบทุกส่วนที่มีจริง, คำว่า "หน้า"/"Page" ชิดขวา,
     ส่วนนำใช้เลขหน้า (1)(2) เนื้อหาใช้ 1 2 3

สิ่งที่ "ไม่ใช่" งานคุณ (ตรวจให้แล้ว อย่าทำซ้ำ):
  ระยะขอบ/ขนาดกระดาษ/ฟอนต์/ขนาดฟอนต์/สไตล์ TU_* → check_docx.py
  **เลขหน้าในสารบัญเทียบหน้าจริงเฉพาะรายการที่จับคู่ชื่อได้** และ **คำสำคัญ/Keywords ตัวหนา**
    → check_deep.py ทำแล้ว ผลอยู่ใน work/deep.json
  บทเนื้อหา/caption ตาราง-ภาพ → Agent 2
  ความถูกต้องของการเขียนรายการอ้างอิง → Agent 3

เขียนผลเป็น JSON ตามสัญญาใน agent-contracts.md ลงไฟล์ <WORK>/agent1-frontmatter.json
(format ใช้ domain = "template"; คำผิด/คำติดกัน/อักขระผิดใช้ domain = "spelling") แล้วตอบกลับแค่ path + จำนวน findingแยกตามระดับ
```

## Agent 2 — รูปแบบเทมเพลต (เนื้อหา)

```
คุณคือผู้ตรวจรูปแบบส่วนเนื้อหาของวิทยานิพนธ์ มหาวิทยาลัยธรรมศาสตร์

อ่านไฟล์เหล่านี้ก่อนเริ่ม:
  <SKILL>/references/inspection-checklist.md   (ตรวจเฉพาะหมวด B5–B6)
  <SKILL>/references/docx-spec.md              (เกณฑ์ตัวเลขของ profile <PROFILE>)
ชิ้นงานของคุณ: <INPUTS>   (ดูจาก agent_plan ใน work/manifest.json)
  **ไฟล์นี้ถูกคัดมาแล้ว** — ร้อยแก้วถูกตัดออกและแทนด้วยบรรทัด "[ตัดร้อยแก้ว N ย่อหน้า …]"
  เพราะกฎที่คุณตรวจไม่ได้ใช้เนื้อความ ส่วนคำผิด/ฟอนต์สคริปต์ตรวจไปแล้ว
  **อย่าทักว่าเนื้อหาหาย** และอย่าขอไฟล์เต็ม บรรทัดสรุปบอกจำนวนย่อหน้ากับช่วงแผ่นไว้ให้
  เล่มหนาจะถูกซอยเป็น body-1.txt, body-2.txt ... **คุณได้รับก้อนของคุณก้อนเดียว**
  ห้ามเปิดก้อนของ agent ตัวอื่น — ตรวจซ้ำแล้ว finding จะซ้ำในรายงาน
  <WORK>/backmatter.txt (ถ้าอยู่ในชิ้นงานของคุณ) — ภาคผนวก/ประวัติผู้เขียน ตรวจด้วยกฎ B7
  ก้อนของคุณเริ่มกลางบทได้ — เรื่องที่ต้องดูข้ามทั้งเล่ม (เลขบทต่อเนื่อง, บทขึ้นหน้าใหม่)
  check_deep.py ตรวจให้แล้ว ไม่ใช่งานคุณ

ขอบเขต:
  B5 หัวข้อบท — "บทที่ X"/"CHAPTER X" อยู่บรรทัดเดียวกึ่งกลาง แล้วชื่อบทบรรทัดถัดไป,
     ชื่อบทภาษาอังกฤษเป็นตัวพิมพ์ใหญ่ทั้งหมดและใช้ "CHAPTER 1" ไม่ใช่ "Chapter 1",
     (เลขบทต่อเนื่องและการขึ้นหน้าใหม่ check_deep.py ตรวจแล้ว ไม่ต้องทำซ้ำ)
  B6 ตาราง/ภาพ — เลขคำบรรยายเป็นรูปแบบ บท.ลำดับ และเรียงตามที่ปรากฏจริง,
     ตารางที่ตกหน้าต้องทวนหัวตาราง + (ต่อ)/(Continued)
     (ตำแหน่ง caption ไม่ต้องตรวจ — ถอดออกจากสกิลแล้ว)
  ความสม่ำเสมอที่มองเห็นจากข้อความ — ระดับหัวข้อย่อยกระโดด (1.1 → 1.1.1.1),
     การนับเลขหัวข้อซ้ำ/ข้าม
     (heading orphan และตารางตกหน้า = เกณฑ์ที่ขึ้นกับการจัดหน้าจริง ต้องมี pagemap.json
      ห้ามสรุปจากเลขแผ่นในป้าย ซึ่งคลาดได้หลายแผ่น)

  B7 ภาคผนวก/ประวัติผู้เขียน — ลำดับหัวข้อ หน้าคั่น และความสม่ำเสมอตามเทมเพลต

สิ่งที่ "ไม่ใช่" งานคุณ: ส่วนนำ → Agent 1 · รายการอ้างอิง → Agent 3 ·
ฟอนต์/ขนาด/ระยะขอบ/สไตล์/สี → check_docx.py · เลขบท + บทขึ้นหน้าใหม่ + ตารางส่วนนำ + บันไดการเยื้อง → check_deep.py

เขียนผลเป็น JSON ตามสัญญาลงไฟล์ <OUT>  (เช่น <WORK>/agent2-body-2.json ตาม agent_plan)
(domain = "template" ทุก finding) แล้วตอบกลับแค่ path + จำนวน finding แยกตามระดับ
```

## Agent 3 — การอ้างอิง APA 7

```
คุณคือผู้ตรวจการอ้างอิง APA 7 ของวิทยานิพนธ์ มหาวิทยาลัยธรรมศาสตร์

ชิ้นงานของคุณ: <INPUTS>   (ดูจาก agent_plan ใน work/manifest.json)
  <WORK>/references.txt หรือ references-N.txt   รายการอ้างอิงช่วงของคุณ
  **หัวไฟล์บอกไว้แล้วว่าก้อนนี้เป็นแหล่งประเภทไหนและให้เปิดคู่มือไฟล์ไหน** — เปิดตามนั้น
  ไฟล์เดียวแล้วใช้กับทุกรายการในก้อน อย่าไล่เดาประเภทแล้วเปิดคู่มือทีละรายการ
  (เจอรายการที่ประเภทไม่ตรงป้าย ให้ตรวจตามประเภทจริงแล้วเขียนบอกไว้ใน issue)
  <WORK>/intext.txt     ย่อหน้าในเนื้อหาที่มีการอ้างอิง — **อยู่ในชิ้นงานของตัวแรกเท่านั้น**
  ถ้าชิ้นงานคุณไม่มี intext.txt แปลว่าเล่มนี้ซอยรายการอ้างอิงหลายก้อน:
  ข้ามข้อ 4 (จับคู่ in-text ↔ รายการท้ายเล่ม) ไปเลย เพราะคุณเห็นรายการไม่ครบทั้งเล่ม
  จะสรุปว่า "อ้างแล้วไม่มีในรายการ" ไม่ได้ — check_deep.py ตรวจกลไกส่วนนี้ให้แล้ว

คู่มือที่ต้องเปิด — **เปิดเท่าที่ใช้ อย่าเปิดทั้งโฟลเดอร์**:

                        แล้วเปิด **เฉพาะไฟล์** ref-NN ของประเภทนั้นไฟล์เดียว
                        (ต้องค้นข้ามหมวดให้ grep ในโฟลเดอร์ apa7-tha-parts/ เอา)
  รายการภาษาอังกฤษ    → <SKILL>/references/apa7-eng/<ประเภทแหล่ง>.md
                        (เช่น "Journal-article-references.md", "Bookebook-references.md")
                        ดูรายชื่อไฟล์ก่อนแล้วเปิดเฉพาะประเภทที่ตรงกับรายการที่กำลังตรวจ

วิธีตรวจ — ไล่ทีละรายการ ห้ามสุ่ม:
  1. แยกภาษาของ "รายการนั้น" ไม่ใช่ของทั้งเล่ม — เล่มไทยที่อ้างงานฝรั่งต้องใช้กฎอังกฤษ
     กับรายการฝรั่ง และกฎไทยกับรายการไทย
  2. กฎไทยที่ต่างจากอังกฤษ (เช็กทุกรายการไทย): ชื่อผู้แต่งไม่กลับคำ (ชื่อ สกุล),
     ปีเป็น พ.ศ. ห้ามแปลงเป็น ค.ศ., ใช้ "และ"/"และคณะ" ไม่ใช่ "&"/"et al.",
     ใช้ "น." ไม่ใช่ "p./pp." (ผู้แต่งต่างชาติที่อ้างในเล่มไทยยังคง p./pp.)
  3. กฎที่ใช้ร่วมกันทั้งสองภาษา: ตัวเอียงลงถูกที่ (ชื่อวารสาร/หนังสือเอียง ชื่อบทความไม่เอียง),
     Title Case สำหรับชื่อวารสาร แต่ Sentence case สำหรับชื่อบทความ,
     ช่วงเลขหน้าใช้ en-dash (–) ไม่ใช่ hyphen (-),
     DOI ต้องเป็น https://doi.org/10.xxxx เท่านั้น (ห้าม "doi:" ห้ามมีจุดปิดท้าย),
     APA7 ตัด "Retrieved from" และตัดที่ตั้งสำนักพิมพ์ออกแล้ว;
     ตรวจ Thai collation เอง (การเรียงอังกฤษอยู่ใน deep.json)
  4. จับคู่ in-text ↔ รายการท้ายเล่ม: อ้างในเนื้อหาแต่ไม่มีในรายการ = critical;
     มีในรายการแต่ไม่เคยอ้าง = major
  5. ข้อมูลต้นฉบับขาด (ไม่มี DOI/ไม่มีวันที่) → บอกว่าขาดใน issue **ห้ามแต่งขึ้นมาเอง**
  6. รายการที่ถูกอยู่แล้วไม่ต้องใส่ใน findings
```

## fan-out — ขยายจำนวน agent ตามขนาดเล่ม

**ไม่เพิ่ม agent ชนิดใหม่ แต่เพิ่มจำนวนตัวของชนิดเดิม** — สัญญาสามแบบข้างบนครอบคลุมงานครบแล้ว
สิ่งที่ขาดคือเล่มหนามีงานเกินกว่าที่ agent ตัวเดียวต่อชนิดจะรับไหว. `split_docx.py` ซอยให้เอง
แล้วเขียน `agent_plan` ไว้ใน `manifest.json`:

| ชนิด | ซอยตาม | เกณฑ์เริ่มต้น | เหตุผล |
|---|---|---|---|
| Agent 1 ส่วนนำ | ไม่ซอย | — | กฎเยอะแต่หน้าน้อย (~10 หน้า) ตัวเดียวจบและซอยแล้วกฎจะขาดจากกัน |
| Agent 2.N เนื้อหา | ความยาว | 60,000 ตัวอักษร/ตัว | ต้นทุนคิดตามปริมาณข้อความที่ต้องกวาดสายตา |
| Agent 3.N อ้างอิง | **จำนวนรายการ** | 60 รายการ/ตัว | ต้นทุนคิดต่อรายการ — แต่ละรายการต้องเปิดคู่มือคนละไฟล์ตามประเภทแหล่ง |

**ทำไม APA7 ต้องซอยด้วยจำนวนรายการ ไม่ใช่ความยาว** — 300 รายการยาวรวมแค่ ~30 KB
(สั้นกว่าเนื้อหาหนึ่งบท) แต่ใช้เวลามากที่สุดในเล่ม เพราะทุกรายการต้องแยกภาษา เดาประเภทแหล่ง
แล้วเปิดไฟล์คู่มือของประเภทนั้น. ซอยด้วยความยาวจะได้ก้อนเดียวเสมอ — คอขวดไม่หาย

**กติกาที่เพิ่มมากับ fan-out**

- **ก้อนสุดท้ายของ body รับ `backmatter.txt` ไปด้วย** — ภาคผนวกไม่ควรเป็น agent แยกตัว งานน้อยเกิน
- **`intext.txt` ไปกับ Agent 3.1 ตัวเดียว** — การจับคู่ in-text ↔ รายการท้ายเล่มต้องเห็นรายการครบทั้งเล่ม
  ตัวที่ 3.2 ขึ้นไปเห็นแค่ช่วงของตัวเอง ถ้าให้ตรวจด้วยจะได้ false positive ว่า "อ้างแล้วไม่มีในรายการ"
- **แต่ละตัวเขียนไฟล์ JSON ของตัวเอง** (`agent2-body-2.json`, `agent3-apa7-3.json` …)
  แล้ว `make_report.py work/auto.json work/deep.json work/agent*.json` รวมให้เอง เรียงตามแผ่นงาน
- **จำนวน agent ไม่ใช่ยิ่งมากยิ่งดี** — เล่มบาง (< ~60 หน้า, < 60 รายการ) `agent_plan` จะได้ 3 ตัวเท่าเดิม
  ซอยเกินจำเป็นแปลว่าจ่ายค่า overhead การอ่านคู่มือซ้ำในทุกตัวโดยไม่ได้อะไรกลับมา

## งานของ orchestrator (ห้ามมอบให้ agent)

1. **ตัดชิ้นงาน** — `python3 scripts/split_docx.py "<ไฟล์>.docx" -o work/`
   ซอยให้เองอัตโนมัติ: body ก้อนละ 60,000 ตัวอักษร (`--max-chars`) และรายการอ้างอิงก้อนละ
   60 รายการ (`--max-ref-entries`) แล้วเขียน **`agent_plan`** ลง `work/manifest.json` —
   บอกครบว่าต้อง spawn กี่ตัว ตัวไหนอ่านไฟล์อะไร เขียนผลลงไฟล์ไหน **ห้ามคิดแผนเอง อ่านจากตรงนี้**
2. **รันตัวตรวจอัตโนมัติแบบโหลดไฟล์ครั้งเดียว**
   ```bash
   python3 scripts/check_all.py "<ไฟล์>.docx" \
       --auto-json work/auto.json --deep-json work/deep.json
   ```
3. **spawn agent ทุกตัวใน `agent_plan` พร้อมกันในเทิร์นเดียว** ด้วย prompt ข้างบน แทนที่
   `<SKILL>` `<WORK>` `<PROFILE>` `<INPUTS>` `<OUT>` ด้วยค่าจริงจาก `work/manifest.json`
   (เล่มบางได้ 3 ตัวเท่าเดิม เล่มหนาได้ 6–9 ตัว) — ดู [fan-out](#fan-out--ขยายจำนวน-agent-ตามขนาดเล่ม)
4. **รวมผลเป็นรายงาน** — deterministic ล้วน ไม่ต้องใช้ agent:
   ```bash
   python3 scripts/make_report.py work/auto.json work/deep.json work/agent*.json --docx "<ไฟล์>.docx" \
       -o "<ไฟล์>_report.docx" --title "<ชื่อวิทยานิพนธ์>"
   ```
   **`auto.json` ต้องมาเป็นไฟล์แรกเสมอ** — `make_report.py` เอา metadata (ชื่อไฟล์/profile/
   เวลาสแกน) จากไฟล์แรก แล้วต่อ findings จากไฟล์ที่เหลือ พร้อมนับ 🔴🟠🟡 ใหม่ทั้งกอง
   ไฟล์ agent ที่หายไปข้ามได้ สคริปต์ไม่พัง
5. **ตรวจก่อนส่ง** — `make_report.py` ตรวจ schema ของสามตารางให้อัตโนมัติ. ถ้าต้องตรวจไฟล์เดิมให้รัน
   `python3 scripts/verify_report.py "<รายงาน>.docx"`. ยืนยัน `template`/`spelling`/`apa7` อยู่ตาราง 1/2/3
   และแต่ละตารางเรียงแผ่น 1 → N. การ render **รายงาน** เป็นภาพเป็น optional QA เท่านั้น
   (ไม่ต้อง spawn agent ซ้ำ) — ขั้นตอนปกติไม่ต้องใช้ LibreOffice เลย

## เมื่อ harness spawn ขนานไม่ได้

รัน prompt ทั้งสามตามลำดับในเทิร์นเดียวกันได้เลย — ผลลัพธ์เหมือนกันทุกประการ
เพราะ agent ไม่ได้คุยกันและไม่ได้อ่านผลของกันและกัน ต่างกันแค่เวลารวม
สัญญาทั้งหมดในไฟล์นี้ตั้งใจออกแบบให้ไม่มี dependency ระหว่าง agent ด้วยเหตุผลนี้
